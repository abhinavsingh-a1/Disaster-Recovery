# Security

## Controls

| Control | Implementation |
|---|---|
| No long-lived keys | Replication agent uses an instance role; CI uses GitHub OIDC |
| Private workloads | Servers, recovery instances, DB and replication servers sit in private subnets; only ALBs are public |
| Private replication | `PRIVATE_IP` data plane over VPC peering; replication SG allows TCP 1500 only from the peer VPC CIDR |
| Least exposure | Default SGs emptied; app SGs accept HTTP only from their ALB SG; DB SGs accept 5432 only from app/recovery SGs |
| Encryption at rest | CMKs (rotation on) for DRS staging disks and snapshots, RDS, Backup vaults; encrypted root volumes; secrets in Secrets Manager |
| Encryption in transit | Optional HTTPS (TLS 1.3 policy) on both ALBs; TLS-only state bucket; DRS replication traffic is encrypted by the agent |
| Instance hardening | IMDSv2 required on source and recovery instances; SSM Session Manager instead of SSH (no key pairs, no port 22) |
| Ransomware | 7-day PIT snapshots (DR Region, CMK), daily backups copied cross-region into Vault Lock vaults, 7-day secret recovery window |
| Audit | VPC flow logs; runbook executions and API calls in CloudTrail; monthly drill reports |
| Change control | PR checks (checkov, tflint), manual approval for apply |

## Vault Lock modes

- **governance** (default): users with special permission can remove the lock. Good for labs.
- **compliance**: after `backup_compliance_changeable_days`, **nobody, including AWS Support and the root user**, can delete recovery points before retention ends, or delete the vault. Use it only when you mean it.

## Accepted risks (lab defaults)

Documented as checkov skips in `.checkov.yaml`:
- HTTP-only ALBs unless certificate ARNs are provided.
- No WAF and no ALB access logs.
- SNS topics use no CMK, because EventBridge and CloudWatch would need extra key-policy grants.
- Lambdas are not in a VPC and have no DLQ.
- The DB password is generated by Terraform and therefore stored in state. The state bucket is encrypted and access-controlled. For stricter setups, rotate the secret after deployment, or switch to RDS-managed master passwords and replicate the credentials separately.
- The bootstrap deploy role has AdministratorAccess (see CICD.md).

## Recommended additions for production

- GuardDuty (including Malware Protection for EBS), Security Hub and AWS Config in both Regions.
- An SCP that denies `drs:DeleteSourceServer`, `backup:DeleteRecoveryPoint`, `kms:ScheduleKeyDeletion` and `rds:DeleteDBInstance` except to a break-glass role.
- A separate DR/backup account for the vault copies (cross-account backup) to survive a compromised production account.
- HTTPS everywhere and WAF on the public ALBs.
